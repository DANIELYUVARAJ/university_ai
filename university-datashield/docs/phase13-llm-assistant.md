# Phase 13: University DataShield AI Assistant Documentation

## 1. Overview & Objective

The **DataShield AI Assistant** extends University DataShield with an optional local Large Language Model (LLM) advisory interface designed for college project demonstrations, academic presentations, and viva defenses.

It allows university privacy officers, faculty, and student analysts to:
1. Ask conversational questions regarding sensitive-field detection, FERPA compliance, and masking policies.
2. Inspect completed synthetic schema scans and receive plain-language explanations of sensitive findings.
3. Understand why specific fields are classified as Direct Identifiers, Quasi-Identifiers, or Sensitive Attributes.
4. Review recommended protection policies (`MASK`, `HASH`, `GENERALIZE`, `SUPPRESS`) alongside the authoritative status from DataShield's deterministic `PolicyEngine`.
5. Understand fail-closed publication-blocking verdicts before publishing to analytical data warehouses.

### Advisory Security Boundary
- **Advisory Only:** LLM output is strictly advisory. Under no circumstances can the LLM approve an analytical publication or override server-side `BLOCK` or `REVIEW` decisions.
- **Fail-Closed Gate:** The existing server-side `PublicationGate` and role-based access control (RBAC) remain authoritative.
- **Mandatory Policy Validation:** Suggested protection actions generated by the model are cross-checked against DataShield's deterministic `PolicyEngine` (v1.0).

## 3. Installation & Local Model Setup

University DataShield uses [Ollama](https://ollama.com) as an optional, privacy-preserving local LLM provider. No cloud API keys or external outbound connections are required.

### Host Status on Current Environment
- **Host Check:** Ollama binary is **not installed** on this host (`Get-Command ollama` returned not found; port 11434 is closed).
- **Graceful Degradation:** The backend gracefully detected the absence of Ollama, reported `available: False`, and seamlessly activated its deterministic fallback engine.

### Setup Instructions for Viva / Live Demonstration
If an examiner or presenter wishes to connect a live local LLM:

1. **Install Ollama:**
   - Windows: Download installer from [https://ollama.com/download](https://ollama.com/download)
   - macOS / Linux: `curl -fsSL https://ollama.com/install.sh | sh`

2. **Pull the Recommended Lightweight Model:**
   ```powershell
   ollama pull llama3.2
   ```

3. **Verify the Ollama Daemon is Running:**
   ```powershell
   ollama run llama3.2
   # Or verify the health endpoint:
   curl http://localhost:11434/api/tags
   ```

4. **Restart / Refresh DataShield:**
   - In the frontend Assistant panel, click **"Refresh Status"**. The badge will transition from amber to emerald (`Ollama Active (llama3.2)`).

## 4. Environment Variables

All LLM configuration resides in environment variables with safe defaults in `.env` and `.env.example`:

| Variable | Default Value | Description |
| :--- | :--- | :--- |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Base HTTP endpoint for the local Ollama API |
| `OLLAMA_MODEL` | `llama3.2` | Local model tag (e.g. `llama3.2`, `phi3`, `mistral`) |
| `OLLAMA_TIMEOUT_SECONDS` | `5.0` | Maximum seconds before timing out and falling back |
| `LLM_ASSISTANT_ENABLED` | `true` | Boolean flag enabling the assistant service |
| `LLM_MAX_PROMPT_CHARS` | `1000` | Hard cap on user prompt characters to prevent buffer exhaustion |

Safe placeholder snippet in `.env.example`:
```env
# Phase 13: Local LLM Assistant (Optional / Advisory)
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=llama3.2
OLLAMA_TIMEOUT_SECONDS=5.0
LLM_ASSISTANT_ENABLED=true
LLM_MAX_PROMPT_CHARS=1000
```

## 6. Example Questions & Synthetic Test Scenarios

### Example Viva Questions Tested
1. **"Why should student_email be masked before analytics publication?"**
   - *Explanation:* Under FERPA (34 CFR Part 99) and university privacy regulations, student email is a direct personal identifier that enables immediate re-identification across educational records. It requires `MASK` or `HASH` before analytical dataset publication.
2. **"Why is placement_package sensitive compensation data under university policy?"**
   - *Explanation:* Placement package and salary offers represent sensitive financial attributes that could lead to financial profiling and identity linkage when combined with academic discipline. It requires `GENERALIZE` (e.g., salary bands) or `SUPPRESS`.
3. **"What happens if student_identifier is published without hashing?"**
   - *Explanation:* Student ID is a direct unique institutional identifier. Publishing without cryptographic hashing triggers an immediate `BLOCK` at the publication gate.
4. **"Why can attendance_percentage be published without masking?"**
   - *Explanation:* Academic performance metrics that cannot independently identify a specific student are classified as academic aggregate attributes (`ProtectionAction.NONE`), permitting analytical aggregation provided direct identifiers are removed.

### Synthetic Schema Test Scenario
The system tests against a 100% synthetic student dataset schema:
- `student_email`: string, `student_001@university.edu` (Direct Identifier -> `MASK`)
- `attendance_percentage`: numeric, `88.5%` (Academic Data -> `NONE`)
- `placement_package`: numeric, `1200000` (Sensitive Attribute -> `GENERALIZE`)
- `student_identifier`: string, `STU-2024-9876` (Direct Identifier -> `HASH`)

**Zero real student data is used in any test fixture, synthetic schema, or documentation.**

## 8. Privacy Safeguards & Data Minimization

The DataShield LLM Assistant adheres to strict Privacy by Design principles:
1. **Zero Raw PII Transmitted:** The LLM client only receives synthetic column names, inferred data types, and confidence scores. No student names, social security numbers, real email addresses, or database table dumps are ever transmitted.
2. **Regex PII Interceptor:** Prompts submitted to `/api/assistant/ask` pass through a client sanitization filter that intercepts and masks patterns resembling emails or real IDs (`[MASKED_PII]`).
3. **No Code / Query Execution:** Model outputs are treated strictly as read-only advisory text strings. The application never executes SQL queries, shell commands, or Python code suggested by the LLM.
4. **No Prompt Persistence:** Prompts and raw model interactions are excluded from persistent audit logs to prevent prompt accumulation and sensitive parameter leakage.
5. **No Hallucinated Replacement:** When Ollama is unavailable, the backend returns clear, honest setup instructions and deterministic domain guidance; it never fabricates simulated AI persona outputs.

## 9. Limitations & Offline Behavior

1. **Host Without Local Ollama:** When Ollama is not installed or active on `localhost:11434`, the assistant status endpoint accurately reports `available: false` with installation instructions. The application runs autonomously in deterministic mode.
2. **Advisory Decision Ceiling:** The LLM has zero capability to alter security states, approve publication requests, or clear audit exceptions.
3. **Model Knowledge Window:** Recommendations are strictly bound by the active policy version (v1.0) configured within University DataShield.
